# 后续质量改进实施规划

> 状态：已实施（A、B、C、E 已完成；D 采用稳定的 Node.js CI + 发布前隔离手动装配方案）。
> 编写日期：2026-08-25。
> 当前基线：`dsh-deepseek-billing@0.1.1`，适配 DSH `0.1.1-rc.2`。

## 1. 背景与结论

当前实现已经覆盖凭据隔离、endpoint 信任边界、完整响应超时、响应大小限制、字段白名单、并发合并、路由限流、browser-trust fence、请求取消、实时国际化和命令生命周期。现有自动测试、入口语法检查、`package.json` 解析和发布包 dry-run 均可通过，暂未发现需要立即修复的高危安全问题。

后续工作以**补齐边界、提高回归可见性和改善失败体验**为主，不重写双端架构，也不扩大凭据或远程访问边界。实施顺序遵循“先正确性与自动防线，再做 UI 行为，最后处理发布维护项”。

## 2. 目标

1. 防止极端 `timeoutMs` 触发 Node.js 定时器溢出，保证配置语义与实际行为一致。
2. 在客户端对本地路由响应增加最小结构校验，避免畸形成功响应进入 React 渲染。
3. 建立覆盖受支持 Node.js 版本的持续集成，自动检查测试、语法和发布包边界。
4. 提高客户端测试的失败定位能力，并逐步覆盖真实 DOM、ARIA、主题和 DSH 装配行为。
5. 在刷新失败时保留最近一次成功余额，并让加载、成功、空态和错误变化可被辅助技术感知。
6. 修正文档目录和发布元数据中的维护性缺口。

## 3. 非目标

- 不改变 API Key 的获取方式，不让凭据进入客户端、响应、日志、文档、截图或测试数据。
- 不放宽余额路由的 loopback-only 策略；远程余额访问仍需等待 DSH 提供正式鉴权/会话边界。
- 不改变五个固定错误码、HTTP 路径、命令名、插件名、客户端模块 ID 或四字段余额模型。
- 不在本轮加入自动轮询、余额告警、消费历史、趋势预测或自动充值。
- 不在没有可靠需求和 API 契约设计前支持多币种聚合。
- 不为了拆分源码引入构建链；`lib/index.js` 和 `lib/client.js` 继续作为真实发布入口。

## 4. 优先级与阶段

| 阶段 | 优先级 | 内容 | 是否改变公开行为 |
|---|---|---|---|
| A | P1 | `timeoutMs` 上限、客户端响应校验 | 是：收紧非法配置；正常响应不变 |
| B | P1 | CI、测试拆分、覆盖率基线 | 否 |
| C | P2 | 刷新失败保留旧余额、ARIA/live region | 是：UI 失败态改善 |
| D | P2 | 真实浏览器与 DSH 装配自动化 | 否，但可能新增开发依赖 |
| E | P3 | 文档目录、npm 发布元数据 | 否 |

阶段 A、B 可在同一迭代完成，但应拆成独立提交，便于审查与回退。阶段 C 涉及可见 UI，必须同步中英文文案、测试、设计文档和截图。阶段 D 先做可行性验证，不直接把重量级工具加入必跑流程。

## 5. 阶段 A：运行边界加固

### 5.1 限制 `timeoutMs`

当前实现已把 `timeoutMs` 限制为有限数值 `0 < timeoutMs <= 120_000`。Node.js 的 `setTimeout()` 无法正确表达任意大的毫秒值，过大值可能产生溢出告警并被缩短为极小延迟。

实现结果：

1. `lib/index.js` 使用 `MAX_TIMEOUT_MS = 120_000`（2 分钟）。
2. 接受区间为 `0 < timeoutMs <= MAX_TIMEOUT_MS`，继续允许小数毫秒。
3. 启动错误消息明确给出上限，不回显其他配置或 endpoint。
4. `test/index.test.js` 覆盖默认/上限/小数通过，以及 `0`、负数、`NaN`、`Infinity` 和超限拒绝。
5. 已同步 README、中英文配置说明和宿主设计文档。

这是公开配置行为的收紧，应随下一次版本发布说明。若实施时发现合法本地代理确实需要超过 2 分钟，先调整上限决策，不绕过定时器安全边界。

### 5.2 客户端响应结构校验

宿主路由已经验证上游数据，客户端现已增加小型纯函数，只接受：

- `{ ok: true, balance: null }`；或
- `{ ok: true, balance }`，且 `balance` 的 `currency`、`total_balance`、`granted_balance`、`topped_up_balance` 均为非空字符串；
- 非 2xx 错误响应只读取已知稳定错误码，未知或畸形形状回退到现有稳定错误路径。

畸形 2xx 响应统一呈现 `invalid_response`，不得把原始 JSON、异常堆栈或内部字段显示到 UI。客户端校验是纵深防御，不替代宿主字段白名单，也不扩展余额响应字段。

测试至少覆盖：合法余额、合法空余额、缺少字段、错误字段类型、未知错误码、非 JSON 响应以及取消请求不更新状态。

### 5.3 阶段 A 验收

- 所有现有正常余额、空余额和固定错误码行为保持不变。
- 极端 `timeoutMs` 在插件启动时稳定失败，不进入 `setTimeout()`。
- 畸形成功响应只产生本地化的 `invalid_response`，React 不接触畸形字段。
- 全部自动测试和静态检查通过，安全日志约束不变。

## 6. 阶段 B：持续集成与测试可维护性

### 6.1 CI 工作流

新增 `.github/workflows/ci.yml`，在受支持的 Node.js 基线上运行矩阵：

- Node.js `22.19.x`；
- Node.js `24.x`。

每个环境至少执行：

```bash

node --check lib/index.js
node --check lib/client.js
node -e "JSON.parse(require('fs').readFileSync('package.json'))"
npm run test:coverage
npm pack --dry-run
```

工作流不得读取真实 DSH home 或真实 API Key。若 npm/DSH 安装步骤未来需要网络，应固定目标版本并保持 lockfile/缓存策略可审查。

### 6.2 拆分客户端测试

保持 `node:test`，把当前大型客户端用例按行为拆分，优先形成以下独立失败单元：

1. 模块 ID、React require 和服务注入；
2. zh/en 词典键一致性与动态侧栏标签；
3. 初始加载、成功、空态和固定错误码；
4. 刷新取消、卸载取消和过期结果隔离；
5. 空白会话临时 notice 的发布、归属、到期和清理；
6. 命令行插槽在 blank-origin 与 active session 中的显示规则。

测试拆分只改变组织方式，不重写轻量 hook harness，也不把模拟 Context 当成真实 DSH 装配证明。

### 6.3 覆盖率策略

先在 CI 中生成 Node.js 原生测试覆盖率报告，用于观察趋势，不立即设置阻断阈值。基线稳定并完成测试拆分后，再决定是否采用门槛；门槛应分别看宿主端与客户端，避免整体数字掩盖客户端缺口。

### 6.4 阶段 B 验收

- 两个 Node.js 基线均通过完整检查。
- dry-run 发布包仍只包含预期入口、patch、README 和 package metadata。
- 客户端主要行为可以从测试名称直接定位，单个失败不再只显示一个总括用例。
- CI 和测试夹具中不存在真实凭据、用户路径或生产账户数据。

## 7. 阶段 C：刷新失败体验与无障碍

### 7.1 保留最近一次成功余额

已调整客户端状态模型，区分“当前可展示结果”和“最近一次刷新错误”：

- 首次加载失败：继续显示当前完整错误态；
- 已有成功余额后刷新失败：保留余额和最后成功更新时间，另显示非阻塞错误提示；
- 下一次刷新成功：清除刷新错误并更新余额与时间；
- 空余额也是一次成功结果，不与请求失败混淆；
- 新请求和卸载仍先取消旧请求，过期结果不得覆盖新状态。

新增 zh/en 文案应保持 `settings.billing` 键集完全一致，所有可见字符串继续通过 `t(key)` 获取。

### 7.2 ARIA 与状态播报

已实现的最小改动：

- 给 section 标题分配稳定 id，并通过 `aria-labelledby` 关联；
- 内容区根据加载状态设置 `aria-busy`；
- 成功、空态和非阻塞刷新结果使用礼貌级 live region；
- 首次请求失败继续使用 `role="alert"`；
- 避免同一消息同时处于多个 live region，防止重复朗读；
- 保留刷新按钮的 `aria-label`、焦点样式和禁用语义。

### 7.3 同步材料

由于本阶段改变可见 UI，需要同步：

- `test/client-render.test.js`；
- `docs/design/client.md`、`i18n.md`、`verification.md`；
- 中文和英文 README 中涉及失败状态的说明；
- `docs/image_zh.png`、`docs/image_en.png`，前提是真实浏览器复核后截图确有变化。

本轮新增的是失败态文案和语义属性；现有截图展示的正常余额态布局与视觉样式没有改变。由于当前未引入真实浏览器运行时，不生成未经复核的失败态截图；发布前若实际视觉检查发现正常态或失败态需要示例，再补充截图。

### 7.4 阶段 C 验收

- 刷新失败不清除最近一次成功余额，首次失败仍显示完整错误态。
- zh/en 切换后新增提示即时更新，不需要重新请求。
- 键盘焦点、禁用状态、窄屏、明暗主题和 screen-reader 播报通过手动检查。
- 取消、卸载和过期结果隔离测试继续通过。

## 8. 阶段 D：真实浏览器与 DSH 装配自动化

本阶段已完成技术可行性验证，结论是暂不引入 Playwright 或 DSH CLI 到 PR 必跑依赖。当前 CI 环境没有锁定的浏览器运行时、本地 `dsh` 命令或项目 lockfile；直接加入会扩大下载、缓存和版本维护面。采用 Node.js CI 必跑，真实浏览器/DSH 装配继续使用隔离临时 home、受控 loopback mock endpoint 和专用虚假凭据的发布前手动清单，不连接 DeepSeek 生产接口。

未来自动化的目标清单（当前由下方发布前手动清单覆盖）：

1. 插件宿主与客户端模块成功装配；
2. 设置页正常出现，zh/en 切换即时更新；
3. 正常、空、缺失凭据、超时和非法响应状态；
4. 连续刷新与离开页面后的取消；
5. 明暗主题、`620px` 以下布局、键盘焦点与主要 ARIA 属性；
6. `/deepseek-billing` 在空白会话和已激活会话中的生命周期；
7. 非 loopback Host 访问余额路由仍返回 `403`。

后续决策门：

- 若工具需要新增 Playwright 等依赖，先记录安装体积、运行时间、浏览器缓存和维护成本；
- PR 必跑任务应保持稳定且无需密钥；不稳定或较慢的真实装配可以先作为发布前/定时任务；
- 不使用截图像素比较替代结构、交互和可访问性断言；截图只覆盖确有视觉回归价值的页面。

## 10. 延后事项

### 10.1 多币种

当前只返回 `balance_infos[0]`。支持多币种需要同时改变服务返回模型、HTTP 响应、命令输出、客户端布局、测试和文档，属于公开接口变更。实施前必须确认 DeepSeek API 对多条余额的顺序与语义，且不同币种不得直接相加。

### 10.2 自动刷新与余额告警

自动轮询会增加上游请求、限流竞争和组件后台生命周期复杂度；余额告警还需要持久化阈值、通知权限和可靠调度。现阶段继续保持“打开页面时加载 + 手动刷新”，除非出现明确用户需求。

### 10.3 远程访问

在 DSH 提供可复用的身份认证、授权和 CSRF 边界前，不通过 `trustedHosts` 或自定义 header 放开余额路由。
